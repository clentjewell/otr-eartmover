# OTR tyre-data RAG — accuracy-first ingestion and retrieval (trial, local-first)

An ingestion pipeline and retrieval layer that answers technical OTR tyre
questions from a fixed corpus of publicly available manufacturer databooks and
reference material. The data informs load, rim, and inflation decisions on
mining and earthmoving tyres, so a wrong figure is a safety risk and a legal
exposure. The system is **safe by design**: numeric specifications are never
generated by a language model and never published without verification and a
human sign-off. When in doubt, it abstains and points to the OEM.

This is the **local-first trial**. Outputs are portable JSON + a SQLite
database + a CSV review queue, structured to port cleanly to Cloudflare
(D1 / Vectorize / R2) and Airtable later. Those dependencies are not added now.

British/Australian English throughout. No icons or emoji.

---

## The two tracks

**Track A — verified structured specifications.** Every spec row is extracted by
two independent passes, diffed cell by cell, validated, and saved with full
provenance (source file, page, and an image crop of the originating table
region). Numbers are served by **exact lookup, verbatim, with citation** — a
language model is never in the path when a number is returned to a user.

**Track B — prose retrieval.** Narrative content (fitting, maintenance,
application guidance, TKPH/WCF methodology, glossary material) is chunked,
embedded, and answered by retrieval-augmented generation, strictly constrained
to retrieved context, with a disclaimer and citation on every answer.

The two never cross: a specific size/TRA-code spec question is answered only
from the signed-off Track A set, or it abstains. It is never answered from prose.

---

## Safety model — how a wrong number is prevented

1. **Dual-pass extraction.** Two independent models (or two passes) must agree.
2. **Validation gates** on every numeric field: units sanity (the classic, and
   dangerous, kPa/psi swap), physically plausible OTR range checks, and
   cross-field geometry (overall diameter vs rim vs section width). Any failed
   gate forces `needs_review`, regardless of A/B agreement.
3. **Source crops.** Every spec row stores an image crop of its source table
   region. The crop is the ground truth for review and may be shown to end
   users in place of, or alongside, the parsed number.
4. **Abstention by default.** A record is servable only when it is
   high-confidence **and** passes every gate **and** is signed off **and** the
   run was finalised with `--commit`. Everything else stays in the review queue.

## Run order

```bash
# 0. Install (PyMuPDF + numpy; provider calls use urllib, no SDKs needed)
python3 -m pip install -r tyre_rag/requirements.txt

# 1. Sync the Tyre Tech Data Drive databooks into tyre_rag/sources/.
#    OTR + Ag set, straight from Drive public links (no auth needed):
python -m tyre_rag.scripts.sync_sources --list   # preview the plan
python -m tyre_rag.scripts.sync_sources          # download otr + ag
#    A few files need manual/MCP fetch - see sources/README.md.

# 2. Set keys (two different vision-capable models, plus an embed model).
cp tyre_rag/.env.example tyre_rag/.env && edit  # never commit real keys
export $(grep -v '^#' tyre_rag/.env | xargs)

# 3. Interactive validation FIRST — one databook, inspect before going wide.
python -m tyre_rag.pipeline.run --single sources/<one-databook>.pdf
#    Review: the extracted records, the A/B agreement rate, REVIEW_QUEUE.csv.

# 4. Full unattended run — verified candidates + review queue + morning report.
#    Does NOT publish numbers.
python -m tyre_rag.pipeline.run --all

# 5. Morning: work REVIEW_QUEUE.csv, record sign-offs in scripts/signoff.csv,
#    then finalise the served dataset.
python -m tyre_rag.pipeline.run --all --commit
```

Ask a question against the served set:

```bash
python -m tyre_rag.serve.cli "What rim is recommended for 27.00R49 E-4?"
```

## Execution modes (reported in MORNING_REPORT.md)

| mode | trigger | behaviour |
|---|---|---|
| `dual-provider` | both `EXTRACT_PROVIDER_A_KEY` and `_B_KEY` set | true independent dual pass |
| `single-provider` | one key set | two passes, one model, different settings — **flagged weaker** |
| `no-model-fallback` | no key set | deterministic text-layer heuristic; **never produces a servable record** — proves the pipeline end to end offline |

Likewise, if `EMBED_PROVIDER_KEY` is absent, Track B uses deterministic hashed
embeddings (retrieval plumbing only — semantically weak; out-of-corpus
discrimination is unreliable until a real embed key is supplied).

## Guardrails (the run is unattended)

- **Idempotent and resumable** — per-file (content hash) and per-page
  checkpoints; re-runs skip completed work.
- **Hard cost ceiling** (`MAX_COST_USD`) — on trip, pause cleanly and report.
- **Secrets via env vars only** — `.env.example` is committed; real keys never.
- **`--commit` required** to finalise the served dataset. Without it, the run
  writes candidates and the review queue only.
- **Provenance on every record and chunk** — no record without source file,
  page, and crop.

---

## Mandatory output contract

Every served answer carries: (1) source attribution — manufacturer, edition
year, page; (2) the standing per-answer disclaimer; (3) the site-level standing
notice (rendered in the portal footer and on any technical page). See
`serve/contract.py` for the exact copy.

---

## Public source links in citations

Each citation can carry a link to the canonical public PDF on the web (the
manufacturer's own databook URL), separate from the private R2/Drive copy.
Candidates live in `scripts/sources_public_urls.csv` with a `verified` column.
A URL is surfaced to users **only when `verified=yes`** (a human has confirmed
it points to the exact edition) — until then the citation stays plain text.
`pipeline/sources_meta.py` enforces the gate; `serve/query.py` attaches the URL
to every numeric and prose citation for the matching `source_file`. This keeps
the provenance chain honest: links go live only after sign-off, the same
discipline as the spec figures themselves.

## Scope notes / production hand-off

- The trial serve layer for Track B is **extractive** (returns the retrieved
  passages with citations). In production, the constrained RAG model composes
  prose from exactly those passages and applies the existing Knowledge Portal
  system prompt (`worker/system-prompt.md`) — including its
  rule to decline fictional brands and never invent codes. That LLM-level
  judgement is deliberately out of scope for the offline pipeline; the
  pipeline's own abstention guarantee is the Track A spec-lookup path.
- Porting targets: `spec_records` -> D1 / Airtable; `prose_chunks` + embeddings
  -> Vectorize; `crops/` -> R2 object keys.
